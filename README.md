<a id="features"></a>
## ✨ Возможности

- 🤖 **11 инструментов для MCP-клиента** — файлы (`read_file`, `write_file`, `list_files`, `search_in_files`, `delete_file`, `move_file`), `run_command`, фоновые задачи (`run_background` + `poll_task`), `server_stats`, `make_backup`
- 📊 **Панель «NoVate MCP»** — статистика сервера, проекты, просмотр файлов и скачивание проектов архивом
- 🔑 **Вход в панель через Telegram (OpenID Connect)** — без паролей и токенов: доступ по списку Telegram ID
- ☁️ **Опциональное Reg.Ru Cloud S3** — постоянное хранение проектов без FUSE/mount; `/data` остаётся обычной POSIX FS
- 🗄 **Бэкапы в Telegram** — по расписанию или кнопкой, загрузка локальных бэкапов с проверкой, шифрование AES-256, восстановление в один клик
- 🔔 **Telegram-алерты** — входы в панель, отклонённые попытки, смена настроек, сбои бэкапов
- 🎨 **Современный минималистичный UI на TypeScript (Bun)** — CSS-анимации, тост-уведомления, акцент `#1ED895`, минимальная нагрузка на систему
- ⚙️ **Настройки из панели** — редактирование текущих значений, генерация локальных секретов и возврат к `.env`
- 🔐 **Безопасность по кругу** — Bearer-токен для MCP, OIDC + HMAC-сессии для панели, изоляция папки, контейнеры не от root
- 🌍 **Публичные сайты** — всё, что агент создаст в проекте, сразу открывается по ссылке
- 🔄 **CI/CD из коробки** — пуш в `main` → GitHub Actions → GHCR → `docker compose pull` на сервере

## 🏗 Архитектура

```
MCP-клиент ──HTTPS + Bearer──┐
                             ▼
                     ДОМЕН (Caddy, авто-HTTPS)
                             │
             ┌───────────────┼─────────────────┐
             ▼               ▼                 ▼
          /mcp/          /projects/            /
             │               │                 │
             ▼               ▼                 ▼
       mcp:8000      статика проектов   dashboard:8001
       (FastMCP,     (публичный          (панель на Bun + TS,
        4 инстр.)     просмотр сайтов)    вход через Telegram OIDC)
                             │
                             ▼
                   ./projects на сервере —
                   единственная папка, доступная MCP

       backup (фоновый сервис): tar.gz проектов и настроек панели ->
       ./backups (последние BACKUP_KEEP копий) + отправка в Telegram
```

GitHub Actions собирает **три образа** из одного Dockerfile (multi-stage)
в один GHCR-пакет с тегами `mcp-latest`, `dashboard-latest` и `backup-latest`.

<a id="quick-start"></a>
## 🚀 Быстрый старт

### Шаг 1. Подготовь репозиторий (один раз)

1. Запушь все файлы, включая `.github/workflows/build.yml`.
2. Вкладка **Actions** → дождись зелёной галочки ✅ (все три образа собраны).
3. **Сделай пакет публичным** (GHCR-пакеты по умолчанию приватные!):
   GitHub → Packages → `novate-mcp` → Package settings → Change visibility → **Public**.
   Один пакет, три тега — менять видимость нужно один раз.

### Шаг 2. Telegram: бот + OIDC-приложение (один раз)

Одного и того же бота достаточно и для входа в панель, и для бэкапов.

1. В **@BotFather** создай бота (или возьми существующего) — его **токен**
   пригодится для бэкапов (`TG_BOT_TOKEN`).
2. Настройки OIDC живут в **мини-приложении BotFather** (кнопка «Open» в чате
   с BotFather, не текстовые команды): выбери бота → **Bot Settings → Web Login**.
   Там показаны **Client ID** и **Client Secret** (`TG_CLIENT_ID` / `TG_CLIENT_SECRET`)
   — бери их именно оттуда; Client Secret — это НЕ токен бота.
3. В разделе Web Login добавь в **Allowed URLs** оба адреса:
   `https://ДОМЕН` и `https://ДОМЕН/auth/callback`.
4. Нажми Start в диалоге с ботом — иначе он не сможет прислать тебе бэкап в личку.
5. Узнай свой Telegram ID у **@userinfobot** — впишешь его в `ALLOWED_TG_USERS`.

### Шаг 3. Сервер (Ubuntu 24.04)

Нужны: VPS, домен с A-записью на IP сервера, доступ по SSH.

```bash
# Загрузи install.sh на сервер, затем:
bash install.sh
```

Скрипт сам: обновит систему → поставит Docker → настроит UFW →
скачает инфра-файлы из репозитория → сгенерирует токены →
сделает `docker compose pull` → запустит всё.

### Шаг 4. Заполни .env

```bash
nano ~/mcp-server/.env
# TG_CLIENT_ID, TG_CLIENT_SECRET — из шага 2
# ALLOWED_TG_USERS — Telegram ID через запятую (кому разрешён вход в панель)
# TG_BOT_TOKEN, TG_CHAT_ID — бот и чат для бэкапов
cd ~/mcp-server && docker compose up -d
```

### Шаг 5. Проверка

```bash
curl -i https://ДОМЕН/mcp/      # ожидается: 401 Unauthorized
```

- `https://ДОМЕН/` — страница входа панели с кнопкой «Войти через Telegram»
- `https://ДОМЕН/projects/` — публичный просмотр проектов

### Шаг 6. Подключение MCP-клиента

Подойдёт любой клиент с поддержкой MCP по HTTP и Bearer-авторизации:

| Параметр | Значение |
|---|---|
| URL | `https://ДОМЕН/mcp/` |
| Аутентификация | Bearer Token |
| Токен | `MCP_TOKEN` из `~/mcp-server/.env` |

<a id="dashboard"></a>
## 📊 Панель управления

Вход — только через Telegram (OpenID Connect): нажми «Войти через Telegram»,
подтверди вход в приложении Telegram — готово. Подписанная HMAC-cookie
живёт 7 дней. Доступ есть только у Telegram ID из `ALLOWED_TG_USERS`,
а ID отклонённых попыток входа видны в логах: `docker compose logs dashboard`.

- **Проекты** — карточки с размером, числом файлов и датой изменения.
  «Открыть сайт» показывается только при наличии `index.html` в корне проекта;
  «Скачать» потоково формирует совместимый с Windows ZIP прямо в HTTP-ответе.
  ZIP хранит размеры файлов в центральном каталоге, быстро открывается после загрузки
  и не требует временного архива на сервере; используется быстрое сжатие.
- **Файлы** — навигация по папкам, скачивание файлов и папок, рекурсивный
  размер папок и дата изменения для каждого файла и каталога.
- **Бэкапы** — статус последнего бэкапа, локальные архивы со скачиванием,
  кнопки «Сделать бэкап сейчас» и «Загрузить бэкап». Единственная кнопка
  загрузки открывает выбор файла и сразу отправляет выбранный архив. Файл
  проверяется по имени, tar.gz/AES-256 формату, структуре `projects/`,
  небезопасным путям, ссылкам и специальным файлам.
- **Статистика** — проектов/файлов (с анимированными счётчиками),
  занято и свободно на диске, аптайм сервера.
- **Настройки** — переопределение значений из `.env` (см. ниже).
- **Версии** — установленный канал/релиз, проверка GitHub Releases, changelog и выбор подписанной версии для обновления. Панель не получает Docker socket: запрос передаётся хостовому systemd-runner, который вызывает `deploy.sh` с проверкой Cosign, readiness и автоматическим rollback.
- **Поиск и фильтры** — мгновенный поиск по названиям проектов, файлов и папок;
  фильтрация по типу и периоду изменения; сортировка по названию, дате, размеру
  и числу файлов без перезагрузки страницы.
- **Уведомления** — единая тост-система в правом верхнем углу с автозакрытием.

Технически: сервер на **Bun** без фреймворков (минимум памяти и CPU),
клиентский JS — один минифицированный файл (~1 КБ), вся анимация на CSS
(transform/opacity — работает на GPU), уважает `prefers-reduced-motion`.
Панель монтирует проекты в режиме **только чтение**: изменять файлы
может только MCP.

<a id="s3-storage"></a>
## ☁️ S3 Storage

S3 — **опциональное постоянное хранилище**, а не файловая система контейнера.
NoVate MCP не использует `s3fs`, `rclone mount`, FUSE или другие S3 mounts:

```text
Agent
  ↓
MCP tools / shell
  ↓
/data — обычная локальная POSIX рабочая копия
  ↓
Storage
  ├── LocalStorage → PROJECTS_DIR
  └── S3Storage    → S3-compatible API → Reg.Ru Cloud S3
```

### Настройка Reg.Ru

1. В панели **Рег.облака** активируй «Хранилище S3» и создай один bucket.
2. В разделе **Хранилище S3 → Ключи доступа** создай/скопируй `Access key`,
   `Secret access key` и актуальный `S3 API Endpoint`.
3. Укажи endpoint именно из панели. Для Reg.Ru обычно это
   `https://s3.regru.cloud`; не заменяй его URL публичного bucket.
4. Укажи регион bucket. Если панель показывает пустой регион, уточни актуальное
   значение у поддержки Reg.Ru: NoVate требует явный `S3_REGION` для SigV4.
5. Заполни `.env` и пересоздай MCP-контейнер:

```dotenv
S3_ENABLED=true
S3_ENDPOINT=https://s3.regru.cloud
S3_ACCESS_KEY=<ACCESS_KEY>
S3_SECRET_KEY=<SECRET_KEY>
S3_BUCKET=<BUCKET>
S3_REGION=<REGION>
S3_PREFIX=projects/
S3_EXCLUDE=
S3_RECONCILE_INTERVAL=600
```

Credentials никогда не коммитятся. `S3_SECRET_KEY` не показывается в панели;
`S3_ACCESS_KEY` маскируется. Все S3-параметры меняются только через `.env`, потому
что при старте MCP проверяет конфигурацию, bucket, List/Put/Delete и выполняет
восстановление. После изменения используй `docker compose up -d mcp dashboard backup`.

Чтобы вернуться к прежнему режиму, установи `S3_ENABLED=false` и пересоздай
контейнеры. `PROJECTS_DIR` остаётся локальной рабочей директорией и в обоих режимах.

### Синхронизация

- `write_file` загружает только созданный или изменённый файл (`PutObject`).
- `delete_file` удаляет файл или весь object prefix; локальное удаление откатывается,
  если обязательное удаление в S3 завершилось ошибкой.
- `move_file` использует `CopyObject`, затем `DeleteObject`; для папки — по всем
  объектам prefix. При ошибке локальное перемещение откатывается.
- `run_command` снимает metadata-снимок до команды и после неё загружает только
  новые/изменённые файлы и удаляет исчезнувшие объекты. `/data` остаётся `cwd`.
- `run_background` делает то же после завершения процесса; `poll_task` показывает
  состояние S3-sync, а `/tmp/mcp-tasks` никогда не попадает в S3.
- Перед сетевой операцией желаемое изменение атомарно записывается в постоянный
  outbox `/storage-state/s3-state.json`. При ошибке локальная копия остаётся в `/data`,
  операция возвращает явную ошибку, а worker повторяет запрос с exponential backoff
  от 30 секунд до 1 часа. Очередь переживает пересоздание MCP-контейнера.
- Каждые `S3_RECONCILE_INTERVAL` секунд выполняется полная сверка локального manifest,
  `/data` и реальных S3 keys. Она восстанавливает пропущенные PUT/DELETE и скачивает
  новые объекты, которые были добавлены непосредственно в bucket.

Структура объектов при `S3_PREFIX=projects/`:

```text
bucket/
└── projects/
    ├── landing/index.html
    └── landing/src/app.js
```

Directory marker objects не создаются. При старте выполняется **безопасный merge**:
S3-файлы, отсутствующие локально, скачиваются; локальные файлы, отсутствующие в S3,
загружаются; при совпадении локальный файл сохраняется и становится приоритетной
версией в S3. Ничего локального не удаляется, поэтому существующий `PROJECTS_DIR`
не теряется. `read_file` дополнительно может восстановить отсутствующий локальный
файл из S3. Новые S3 objects также подтягиваются периодической сверкой; если один и
тот же путь существует локально, локальная рабочая версия остаётся приоритетной.

Всегда исключаются `node_modules`, `.git`, `.cache`, `tmp`, `__pycache__`, `*.pyc`,
`*.log` и служебные файлы NoVate. `S3_EXCLUDE` добавляет собственные имена или glob-
паттерны через запятую. Встроенные исключения отключить нельзя, чтобы `npm install`
не загружал сотни мегабайт зависимостей.

### S3 и резервные копии

S3 storage и бэкапы независимы. Backup по-прежнему архивирует текущую `/data` в
`tar.gz[.enc]`, хранит архивы в `/backups` и может отправлять их в Telegram.
После восстановления архива backup создаёт служебный триггер, и MCP переносит
восстановленные изменения в S3. Сами архивы в S3 bucket проектов не загружаются.

### Статус и ручное управление

Вкладка **Настройки → S3-хранилище** показывает подключение, размер постоянной
очереди, последнюю успешную операцию, полную сверку, её результат и безопасный текст
последней ошибки. Там же доступны кнопки **Проверить подключение**,
**Синхронизировать сейчас** и **Восстановить отсутствующие**. Dashboard передаёт
команды через `/config/s3-action.json`, а читает только безопасный
`/storage-state/status.json`; credentials в эти файлы не записываются.

`storage_state` — отдельный именованный Docker volume. Он монтируется в
`/storage-state`, не находится внутри `PROJECTS_DIR`, не архивируется backup и не
публикуется Caddy. Не выполняй `docker compose down -v`, если очередь нужно сохранить.

### Диагностика

```bash
docker compose logs -f mcp
docker compose exec mcp sh -c 'test "$S3_ENABLED" = true && echo enabled'
```

При `S3_ENABLED=true` запуск останавливается сразу, если отсутствует обязательная
переменная, endpoint некорректен, bucket недоступен или нет List/Put/Delete прав.
Сообщения не содержат secret key. Проверь endpoint, region, имя bucket, права ключа,
сетевой доступ и затем выполни `docker compose up -d mcp`.

<a id="backups"></a>
## 🗄 Бэкапы

Фоновый контейнер `backup` раз в `BACKUP_INTERVAL_HOURS` часов
(по умолчанию 24) собирает tar.gz-архив: все проекты + настройки панели.

- Архив складывается в `~/mcp-server/backups/` (хранятся последние
  `BACKUP_KEEP` копий, старые удаляются автоматически).
- Каждый архив отправляется ботом `TG_BOT_TOKEN` в чат `TG_CHAT_ID`
  (личный чат — если указать свой Telegram ID).
- Кнопка **«Сделать бэкап сейчас»** — в панели, раздел «Бэкапы», или инструмент
  `make_backup` из MCP-клиента.
- **Загрузка локального бэкапа**: панель принимает только файлы вида
  `novate-backup-YYYYMMDD-HHMMSS.tar.gz[.enc]` до 512 МБ. Перед сохранением
  проверяются формат, структура NoVate MCP и безопасность содержимого.
  Для проверки `.enc` нужен текущий `BACKUP_PASSWORD`.
- **Восстановление в один клик**: «Восстановить» у любого архива перезаписывает
  проекты из него (перед этим автоматически делается страховочный бэкап;
  настройки панели из архива не восстанавливаются).
- **Шифрование**: если задан `BACKUP_PASSWORD`, архивы шифруются AES-256
  (файлы `.enc`) и в Telegram, и локально. Расшифровка скачанного:
  `openssl enc -d -aes-256-cbc -pbkdf2 -in файл.enc -out файл.tar.gz`.
- Telegram не настроен (нет токена/чата) — бэкапы остаются локальными.
- Архив больше 50 МБ (лимит Bot API) — бот пришлёт уведомление,
  а архив можно скачать в панели или забрать из папки `backups/`.
- Все настройки бэкапов можно менять прямо в панели —
  применяются в течение минуты, без перезапуска.
- Логи сервиса: `docker compose logs -f backup`.

<a id="settings"></a>
## ⚙️ Настройки

Все значения живут в `.env` на сервере (не коммитится!).
Приоритет: **переопределение в панели** > **`.env`** (значения по умолчанию).

| Ключ | Назначение | Смена из панели |
|---|---|---|
| `MCP_TOKEN` | Bearer-токен для MCP-клиента | ✅ генерация и копирование; MCP-процесс применяет автоматически |
| `SESSION_SECRET` | Секрет шифрования сессий панели (AES-256-GCM) | ✅ генерация и копирование; сразу завершает текущие сессии |
| `TG_CLIENT_ID` | Client ID OIDC-приложения Telegram | ✅ сразу |
| `TG_CLIENT_SECRET` | Client Secret OIDC-приложения | ✅ ручная замена (значение выдаёт Telegram) |
| `ALLOWED_TG_USERS` | Telegram ID с доступом в панель, через запятую | ✅ поле с текущим списком: добавление, изменение и удаление |
| `TG_BOT_TOKEN` | Токен бота, присылающего бэкапы | ✅ ручная замена (значение выдаёт Telegram) |
| `TG_CHAT_ID` | ID чата для бэкапов | ✅ редактирование или очистка, в течение минуты |
| `BACKUP_INTERVAL_HOURS` | Интервал бэкапов, часов | ✅ в течение минуты |
| `BACKUP_KEEP` | Сколько архивов хранить локально | ✅ в течение минуты |
| `BACKUP_PASSWORD` | Пароль шифрования архивов (AES-256) | ✅ генерация и копирование, в течение минуты |
| `S3_ENABLED` | Включение постоянного S3-хранилища | 👉 только `.env`, пересоздание контейнеров |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`, `S3_PREFIX` | Подключение и prefix S3 | 👁 статус в панели; изменение только `.env` |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Credentials S3 | 🔒 access key маскируется, secret не раскрывается; только `.env` |
| `S3_EXCLUDE` | Дополнительные исключения синхронизации | 👉 только `.env` |
| `S3_RECONCILE_INTERVAL` | Интервал полной сверки `/data` и S3, минимум 30 секунд | 👉 только `.env` |
| `DOMAIN` | Домен сервера и callback Telegram | 👉 только `.env`, затем `install.sh` |
| `TZ` | Часовой пояс контейнеров (время в панели, логи, бэкапы) | 👉 только `.env`, затем `docker compose up -d` |

Обычные значения отображаются только в полях ввода — их можно дополнять,
исправлять и очищать. Бейдж источника `.env` или `панель` расположен рядом с названием параметра. Локальные секреты (`MCP_TOKEN`, `SESSION_SECRET`,
`BACKUP_PASSWORD`) генерируются панелью и показываются один раз для копирования.
`TG_CLIENT_SECRET` и `TG_BOT_TOKEN` выдаются Telegram и заменяются вручную.
Кнопка **«По умолчанию»** удаляет переопределение — снова действует `.env`.
`PROJECTS_DIR` и `DOMAIN` в панели не показываются: оба параметра меняются через `.env`; для `DOMAIN` после изменения запускается `install.sh`.
Для автоматического применения `MCP_TOKEN` контейнеру dashboard не выдаётся
опасный доступ к Docker socket: MCP-процесс сам отслеживает изменение и делает re-exec.

<a id="security"></a>
## 🔐 Безопасность

- MCP отвергает запросы без токена (проверка: `curl` выше отдаёт 401).
- Вход в панель — Telegram OpenID Connect: PKCE (S256), одноразовый `state`
  в короткоживущей подписанной cookie, подпись `id_token` проверяется по
  публичным ключам Telegram (JWKS), проверяются `iss`, `aud` и `exp`.
- Доступ к панели — только у Telegram ID из `ALLOWED_TG_USERS`; список
  проверяется при каждом запросе, поэтому убранный из списка пользователь
  теряет доступ мгновенно.
- Сессия панели — аутентифицированная AES-256-GCM cookie (ключ выводится из `SESSION_SECRET` через scrypt),
  HttpOnly + Secure + SameSite=Lax, живёт 7 дней.
- Ключ cookie выводится из `SESSION_SECRET` через memory-hard scrypt; целостность и конфиденциальность обеспечивает AES-256-GCM authentication tag.
- Все файловые операции ограничены папкой проектов — защита от `../` в коде
  + Docker-монтирование только этой папки.
- `run_command` выполняется **внутри контейнера**, а не на хосте.
- Контейнеры работают не от root (uid 1000).
- Восстановление из бэкапа запускается только из авторизованной панели;
  перед восстановлением автоматически делается страховочный бэкап.
- Наружу открыты только 80/443 (UFW + Caddy); порты 8000/8001 внутренние,
  сервис бэкапов наружу не торчит вовсе.
- Бэкапы содержат `overrides.json` (там могут быть переопределённые секреты) —
  береги чат с бэкапами и папку `backups/` как секреты.
- Всё в `projects/` публично по ссылкам `/projects/...` — это нужно для
  просмотра созданных сайтов. Панель при этом доступна только после входа.

<a id="releases-health"></a>
## Версии, проверки и здоровье сервисов

### Формат релиза

Релизы используют формат `YY.M.RELEASE.BUILD`, например `26.8.1.001`:

- `YY` — год;
- `M` — месяц;
- `RELEASE` — серия релиза; увеличивается после сборки `999`;
- `BUILD` — трёхзначный номер сборки от `001` до `999`.

Тег релиза автоматически создаёт три версионных образа:

```text
mcp-26.8.1.001
dashboard-26.8.1.001
backup-26.8.1.001
```

Ветка `main` продолжает публиковать `mcp-latest`, `dashboard-latest` и `backup-latest`.
Для закрепления версии или отката задайте в `.env`:

```dotenv
NOVATE_VERSION=26.8.1.001
```

Затем выполните `docker compose pull && docker compose up -d`. Верните
`NOVATE_VERSION=latest`, чтобы снова получать актуальные образы.

### CI и безопасность

Каждый Pull Request проверяет Python, Bun/TypeScript, сборку dashboard,
Docker Compose и сборку всех Docker targets. Отдельный workflow запускает
Gitleaks и Trivy; CodeQL продолжает анализировать Python и TypeScript.

### Healthchecks и просроченные бэкапы

Проверить состояние контейнеров:

```bash
docker compose ps
docker inspect --format '{{json .State.Health}}' fastmcp-server
docker inspect --format '{{json .State.Health}}' mcp-dashboard
docker inspect --format '{{json .State.Health}}' novate-backup
```

MCP получает пятиминутный стартовый период healthcheck, потому что первичная
S3-синхронизация может выполняться несколько минут. Caddy запускается без ожидания
`service_healthy`: временная неготовность одного маршрута не отключает панель и
статические сайты.

Backup-сервис обновляет `/backups/.backup-heartbeat.json`. Если успешной копии
нет дольше автоматического порога `max(2 интервала, интервал + 1 час)`, он один
раз отправляет предупреждение в Telegram. Порог можно задать явно:

```dotenv
BACKUP_STALE_AFTER_HOURS=48
```

История изменений ведётся в [CHANGELOG.md](CHANGELOG.md).

### Защищённые опубликованные проекты

Маршрут `/projects/*` больше не обслуживается Caddy напрямую. Запрос проходит через
панель и требует действующую Telegram OIDC-сессию пользователя из
`ALLOWED_TG_USERS`. После входа пользователь возвращается на исходный адрес проекта.
Каталог проектов не публикуется напрямую через Caddy, directory listing отсутствует,
а ответы получают `Cache-Control: private`. Dashboard имеет запись в `/data` только
для подтверждённого удаления проекта авторизованным пользователем.
В списке проектов доступна кнопка с корзиной: после подтверждения она удаляет
только выбранную top-level папку, отправляет Telegram-уведомление и запускает
немедленную S3-сверку для удаления соответствующих объектов из bucket.

### Мониторинг и Telegram alerts

Раздел **«Мониторинг»** показывает состояние S3, размер очереди, heartbeat backup,
результат restore drill и свободное место. Новые ошибки и последующее восстановление
отправляются в Telegram один раз на смену состояния. Порогами управляют:

- `MONITOR_INTERVAL_SECONDS`;
- `MONITOR_BACKUP_HEARTBEAT_SECONDS`;
- `MONITOR_S3_PENDING_LIMIT`;
- `MONITOR_DISK_FREE_PERCENT`.

### Автоматический restore drill

После создания каждого архива backup-сервис расшифровывает его при необходимости и
распаковывает во временный каталог, не изменяя рабочий `/data`. Проверяются безопасные
пути, читаемость каждого файла и совпадение числа файлов. Результат хранится в
`/backups/.restore-drill.json` и показывается в мониторинге. Отключение допускается
через `BACKUP_RESTORE_DRILL=false`.

### Подписи образов и SBOM

GitHub Actions публикует для каждого MCP/dashboard/backup-образа SBOM и provenance,
а digest подписывает keyless-подписью Cosign через GitHub OIDC. `deploy.sh` после
скачивания образов проверяет digest, issuer и identity workflow до запуска
контейнеров. Проверка включена по умолчанию параметром `NOVATE_VERIFY_SIGNATURES=true`.

### Безопасный deploy и rollback

Для последней сборки или конкретного релиза используйте:

```bash
./deploy.sh latest
./deploy.sh 26.8.1.001
```

На сервере с systemd команда автоматически запускает deploy как transient unit и
сразу возвращает терминал. Имя unit и команды просмотра лога/статуса выводятся при
старте. Для диагностики в текущем терминале используйте:

```bash
./deploy.sh latest --foreground
```

Скрипт блокирует параллельные запуски, сохраняет `.env` и локальные снимки текущих
образов, проверяет Compose, запускает новые контейнеры, ждёт health/readiness и
выполняет smoke-test панели. При ошибке или таймауте прежние образы и `.env`
восстанавливаются автоматически. `NOVATE_DEPLOY_TIMEOUT` задаёт базовое ожидание
readiness, а `NOVATE_S3_STALL_TIMEOUT` — допустимое время без изменения фазы или
счётчика S3. Пока `phase/current/total` меняются, дедлайн сдвигается, поэтому общее
время синхронизации не ограничено количеством файлов.

### Защита от поисковой индексации

Caddy отдаёт `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet, noimageindex`
на всех маршрутах, `robots.txt` с `Disallow: /`, не публикует sitemap и устанавливает
`Referrer-Policy: no-referrer`. Это распространяется на панель, MCP и `/projects/*`.

> Важно: `noindex` убирает сайт из обычной поисковой выдачи, но не делает публичный
> домен секретным. Его всё ещё можно обнаружить через DNS, журналы Certificate
> Transparency и сетевое сканирование. Панель защищена Telegram OIDC, MCP — Bearer
> token, а `/projects/*` теперь требует такую же Telegram OIDC-сессию. Для сетевой изоляции
> добавьте VPN, IP allowlist или Cloudflare Access.

## Администрирование и безопасность

Панель поддерживает предварительную проверку релиза, диагностику systemd runner, историю deploy и безопасный просмотр журналов. Хостовый `host-status.sh` передаёт панели состояния Docker-контейнеров без монтирования Docker socket.

В разделе доступа можно создавать дополнительные MCP-токены с ролями:

- `reader` — чтение файлов, поиск и просмотр статистики;
- `editor` — права reader и изменение файлов;
- `operator` — полное управление, включая команды, удаление и бэкапы.

Все административные действия записываются в аудит. Бэкапы можно проверять вручную и восстанавливать целиком либо только для выбранного проекта. После обновления `install.sh` устанавливает systemd timer для сбора состояния хоста.
